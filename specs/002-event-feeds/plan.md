# Implementation Plan: Event Feeds

**Branch**: `002-event-feeds` | **Date**: 2026-11-07 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/002-event-feeds/spec.md`

## Summary

Publish Atom 1.0 feeds of public upcoming events (one for all events, one per category) as
static files generated by the existing site build, plus a `/feeds/` page, a footer **Follow**
link and autodiscovery. Text is `type="text"` only, built with the standard library's XML
writer, so source text can't become markup. Two optional event fields, `published_at` and
`changed_at`, give entries a correct "listed" order and an "updated" time that moves only when
a follower-relevant detail changes, so rebuilds produce identical files. No sign-up, storage,
Worker or personal data. A PATCH constitution amendment clarifies that feeds are allowed.

## Technical Context

**Language/Version**: Python 3.13 (discovery package `netc`, existing); HTML/CSS (Jinja templates); JavaScript only in existing Playwright tests

**Primary Dependencies**: Existing only: Jinja2, Pydantic, `xml.etree.ElementTree` (stdlib); `feedparser` (already a dependency) used in tests to parse feeds as readers do

**Storage**: `data/events/**.json` (two new optional fields on Event); no new storage

**Testing**: pytest (unit, contract, integration, `-m security`), Playwright + axe (`web/tests`)

**Target Platform**: Static site on Cloudflare Pages (`netechconnect.com`), built by GitHub Actions `deploy.yml`

**Project Type**: Static web site generated by a Python CLI (existing feature 001 layout)

**Performance Goals**: Feeds add < 1 s to a site build; each feed ≤ ~100 KB uncompressed

**Constraints**: No personal data (FR-008); no new services, secrets, workflows or dependencies; byte-identical feeds across builds when no event changed (SC-007); existing CSP and headers; WCAG 2.2 AA

**Scale/Scope**: 12 feeds (1 + 11 categories), ≤ 100 entries each; one new page; tens of new events a month

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*

| Principle | Check | Status |
|---|---|---|
| I. Security by Default | Output encoded for its context (Atom `type="text"`, XML escaping, XML-char filter); no new input, credential, or outbound fetch; no personal data stored, so no justification needed; existing CSP/HSTS/nosniff apply; no new dependency. Threat analysis: research R9. | ✅ |
| II. Aggregator, Not Organizer | Each entry's primary link is the organizer's page; entries carry only the listing summary. No iCal/.ics, calendar subscription, invite or reminder. "Feed ≠ calendar subscription" made explicit by the PATCH amendment (R8), landed **before** the code. | ✅ (with amendment) |
| III. Nebraska Community Scope | Feeds draw from the same public, in-scope events as the site. | ✅ |
| IV. Accurate, Attributed Event Data | Entries link to the original listing; times shown in Central; cancellations shown; `changed_at` signals detail changes. | ✅ |
| V. Responsible & Resilient Discovery | Discovery unchanged except recording two timestamps; source text still untrusted. | ✅ |
| VI. Test-First Quality | Failing tests first: feed contract rules, hostile-text security tests, lifecycle timestamps, build integration, browser + axe for `/feeds/`. | ✅ |
| VII. Accessible, Simple Presentation | One static page, no JS, AA tested at 320/360/1280 light/dark; simplest design (stdlib XML, no copy button, footer link). | ✅ |
| Security Requirements | Threat analysis present (R9); no admin functions, public input, or stored personal data added. | ✅ |
| Workflow | Spec Kit flow; PRs with security pass; CI gates unchanged. | ✅ |

**Post-design re-check (after Phase 1)**: unchanged, all ✅. The design adds no service,
dependency or input; the only data change is two optional timestamps.
